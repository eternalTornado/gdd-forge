# Contract — 2_Core Gameplay.md (lite profile)

**Conventions**: `brief:D-xx` = a decision field from `brief-schema.md` · `lite-N` = one of this profile's other four output files · `tmpl` = `${CLAUDE_SKILL_DIR}/templates/lite/2-core-gameplay.md` skeleton (headings fixed, guidance comments removed in output) · `check` = `${CLAUDE_SKILL_DIR}/checklists/lite/lite-2-gameplay.md` · `data` = `${CLAUDE_SKILL_DIR}/data/<file>`, the only allowed source of external facts. Output language = `brief:D-12`; headings keep the English `2.` prefix in every language. A "N/A section" is still written: heading, one paragraph stating why it is minimal and which decision caused it.

- **Owner / model**: `gdd-mechanics-designer` / **opus** — same agent and discipline as the full profile's `4_Gameplay and Mechanics.md`.
- **Consumes**: `1_Concept.md` in full (§1.3 concept, §1.4 pillars, §1.5 feature set, §1.7 audience/platforms, §1.9 scope/glossary); `brief:D-03, D-09, D-20, D-22, D-23, D-30, D-35, D-43, D-44`. Per `profile-casual.md` § Wave table, this dispatch is dispatched alone (W2, not parallel), so the orchestrator gives it the whole `1_Concept.md` file rather than a script-sliced excerpt — the file targets 3–5 KB, small enough that slicing adds overhead without saving tokens.
- **tmpl**: `templates/lite/2-core-gameplay.md` · **check**: `checklists/lite/lite-2-gameplay.md` · **data**: `data/game-design-patterns.md`; the `data/monetization/` slices `D-06` selects, only if `D-06` is F2P/hybrid (see `data/monetization/_index.md`)
- **Sections**:
  - §2.1 Core Loop — the session loop as a numbered verb cycle (this profile collapses the full profile's 30-second/5-minute/session nesting into one cycle unless the pitch genuinely needs two tiers — casual sessions rarely support three). Cite a §1.4 pillar per beat.
  - §2.2 World Rules — 3–5 short declaratives on what is always true (movement, collision, fail state) — condensed from the full profile's §4.3, no separate physics subsection.
  - §2.3 Mechanics Catalogue — one sub-section per mechanic: intent · rules · inputs/outputs · a tunables table. Every mechanic cites a §1.4 pillar (hard rule, unchanged from the full profile). Casual scope typically yields 2–5 mechanics, not the full profile's open-ended catalogue.
  - §2.4 Economy — sources/sinks table for every currency. If `D-06` is F2P/hybrid, mark which sinks are monetised using only `D-30` mechanisms — identical hard rule to the full profile's §4.7.
  - §2.5 Obstacle & Spawn Patterns — replaces the full profile's `8_Artificial Intelligence.md` entirely. This is **patterns and spawn rules, not AI**: obstacle archetypes, spawn-rate/difficulty-scaling rules, simple enemy movement patterns if `D-22` includes "simple enemies." No perception model, no navmesh, no behaviour tree, no utility/GOAP language belongs here — if the brief implies any of that, it is a GAP that should read "this needs the full profile's `8_Artificial Intelligence.md`, not the lite obstacle-pattern section" (see `profile-casual.md` § When not to use this profile). CONDITIONAL: `D-22 = None` → one line, "No enemies or scripted obstacles beyond terrain/level geometry (D-22)."
  - §2.6 Level / Stage Structure — reflects `D-23`. For `Level select (grid)` or similar discrete structures: a structure map (mermaid or a short list) plus how stages group into difficulty bands. For `Endless`: the meta-structure of an endless run (how a run starts/ends, what escalates over time).
  - §2.7 Difficulty & Pacing Curve — a short table or paragraph plotting how difficulty rises across §2.6's structure, qualitative only, no fabricated benchmark numbers (tunables named, not invented values).
  - §2.8 First Stages / Generator Rules — CONDITIONAL on `D-23`: if a discrete level/stage structure, write the first 10 stages as compact table rows (id · name · mechanic introduced/tested · difficulty tier · target duration `(est.)`) — no full per-level prose entries the way the full profile's §6.4 does; if `D-23 = Endless` (or another generator-driven structure), write the generator rules instead (what generates, constraints/guardrails, authored-vs-generated share per `D-35`) and state plainly that there is no fixed stage list.
  - §2.9 Feature List Table — every feature this file designs, id · feature · pillar (§1.4) · priority · depends-on, cross-referenced to §1.5.
  - Open Decisions — one bullet per `UNDECIDED` brief field and GAP, same format as the full profile.
- **Depth rule**: `D-22 = None` → §2.5 becomes the one-line statement above. `D-23 ∈ {Endless, ...}` → §2.8 becomes generator rules instead of a stage table (see §2.8 above); `D-09 = Micro` → §2.1 stays a single-tier loop, no meta-progression tier added.
- **Hard rules**: every mechanic must cite a §1.4 pillar. Monetised sinks may only use `D-30` mechanisms; anything else is a GAP. §2.5 obstacle/spawn design must not describe perception, navigation, or learning systems — that is an explicit escalation trigger to the full profile, not something to elaborate around.

# Contract — 3_UX Art and Audio.md (lite profile)

**Conventions**: `brief:D-xx` = a decision field from `brief-schema.md` · `lite-N` = one of this profile's other four output files · `tmpl` = `${CLAUDE_SKILL_DIR}/templates/lite/3-ux-art-audio.md` skeleton (headings fixed, guidance comments removed in output) · `check` = `${CLAUDE_SKILL_DIR}/checklists/lite/lite-3-ux-audio.md` · `data` = `${CLAUDE_SKILL_DIR}/data/<file>`, the only allowed source of external facts. Output language = `brief:D-12`; headings keep the English `3.` prefix in every language. A "N/A section" is still written: heading, one paragraph stating why it is minimal and which decision caused it.

- **Owner / model**: `gdd-ux-designer` / **sonnet** — same agent as the full profile's `7_Interface.md`, additionally covering the full profile's `10_Game Art.md` and the game-feel/juice content neither full chapter names on its own.
- **Consumes**: `1_Concept.md` §1.4 (pillars), §1.7 (audience/platforms), §1.8 (setting/theme); `2_Core Gameplay.md` §2.1 (core loop), §2.3 (mechanics catalogue); `brief:D-04, D-07, D-08, D-38, D-39`. Dispatched in W3 alongside the Business and Tech files — all three read only files 1 and 2, never each other, so this dispatch can run fully in parallel with them. Per `profile-casual.md` § Wave table, the orchestrator delivers this dispatch `WORK/_anchor.md` (pillars + glossary) plus script-sliced excerpts of §1.7/§1.8 and §2.1/§2.3 rather than the whole of files 1 and 2 — three parallel dispatches each reading two whole upstream files would otherwise triple the duplicated token cost for content most of which this file never uses.
- **tmpl**: `templates/lite/3-ux-art-audio.md` · **check**: `checklists/lite/lite-3-ux-audio.md` · **data**: the `data/accessibility/` slices `D-39` selects (see `data/accessibility/_index.md`); `data/platforms/mobile.md`
- **Sections**:
  - §3.1 UX Principles — 3–4 principles derived from §1.4 pillars, each testable against a screen decision (same bar as the full profile's §7.1).
  - §3.2 Screen Flow & Inventory — merges the full profile's §7.2 (information architecture) and §7.3 (screen inventory) into one section: a short flow list or mermaid diagram, then a compact table (screen · purpose · key elements). Casual games typically hold 4–8 screens; do not pad this toward the full profile's count.
  - §3.3 HUD & Controls — merges §7.4 and §7.5: persistent on-screen elements tied to §2.3 mechanics, plus the input model per `D-04` (tap/swipe/tilt for mobile — most casual control schemes are one paragraph, not a per-platform table, unless `D-04` genuinely spans multiple distinct input types).
  - §3.4 FTUE & Onboarding — the first-time-user-experience flow: which mechanic from §2.3 is taught first and how (tooltip, forced first level, gesture prompt), tied to §2.8's first stage if one exists.
  - §3.5 Accessibility & Localisation — maps each `D-39` commitment to a concrete feature (same discipline as the full profile's §7.9); states `D-38`'s language list and any text-expansion/font risk. If `D-39 = "None specified"`, state baseline-only and flag it in Open Decisions, exactly as the full profile's Depth rule requires.
  - §3.6 Art Style Guide — condenses the full profile's §10.1–§10.2: 2–3 visual pillars traceable to `D-07`/`D-08`, shape language, palette philosophy, one line on lighting/mood. No per-character or per-region breakdown (casual profiles rarely have a cast — see `1_Concept.md` §1.8's narrative depth rule).
  - §3.7 Asset List & Naming Convention — condenses the full profile's §10.8–§10.9 into one section: the naming pattern (with 2–3 examples) plus a compact asset list (id · type · name · priority). **This is the canonical naming convention for the whole lite output set** — unlike the full profile, no separate art-director chapter competes to define one, so state it once here and expect `5_Tech Note.md` §5.3 to cite it, not redefine it.
  - §3.8 Game Feel & Juice — new section with no full-profile equivalent by this name (the full profile scatters it across §7.6 camera/feedback and §10.5 VFX/animation principles): feedback per event (hit, success, failure, reward), screen shake, particles, haptics, audio stings. This is what makes a casual game read as polished rather than placeholder — do not under-write it relative to §3.2–§3.3.
  - §3.9 Audio Direction — condenses the full profile's §7.7: music style, SFX categories tied to §2.3 mechanics, and the stings §3.8 references. One paragraph on mix priorities.
  - Open Decisions — one bullet per `UNDECIDED` brief field and GAP, same format as the full profile. `D-39 = "None specified"` always appears here per the Depth rule.
- **Depth rule**: `D-20 ≠ None` (rare in a casual preset, but possible on an edited preset) → add a lobby/matchmaking line to §3.2. `D-39 = "None specified"` → §3.5 baseline-only, flagged as Open Decision.
- **Hard rules**: every screen in §3.2 must trace to a mechanic (§2.3), a platform requirement (`D-04`), or an explicit brief need — no screen exists for taste alone. Accessibility commitments in §3.5 come only from `D-39`; do not promise a feature not listed there. The naming convention stated in §3.7 is the one and only naming scheme for this GDD set — `5_Tech Note.md` must not invent a second one.
